# 信息密度与紧凑表达

信息密度优化的目标不是把字号、行高和间距压小，而是让读者在尽量少的滚动中看见同一问题的完整结构。先修正文档语义，再由 Docs Engine 负责一致呈现。

## 何时必须重新选择结构

出现任一信号时，不要继续机械添加列表项：

- 一个列表包含五项以上名词或短词组，每项都不需要单独解释。
- 连续出现两组以上列表，读者必须跨屏记忆前一组才能比较后一组。
- 三个以上分类重复使用“分类标题 → 包括：→ 多个短字段”。
- 标题、“包括：”和列表之间存在多层空行，但真正的信息只有一组名词。
- 读者的主要任务是看全貌、找差异或理解分类，而不是逐项执行。

## 按读者任务选择结构

### 行内并列

同一类别下只有一组短字段，且不需要分别解释时，合并成一句：

```md
食材特征包括重量、初始温度、含水率、肥瘦比例和切片厚度。
```

不要写成五个各占一行的项目符号。

### 紧凑定义行

有二到四个分类，每类只需要一行解释，并且窄屏阅读很重要时，保留少量列表项，但以加粗引导词承载分类：

```md
- **输入条件：** 菜谱版本、食材参数、环境条件和设备状态。
- **过程状态：** 温度曲线、转速、火力、重量和视觉变化。
- **控制动作：** 火力、翻炒、投料、调味和步骤切换。
- **最终结果：** 出品指标、评分、投诉、剩餐和复购。
```

这里每个列表项代表一个真正独立的分类，而不是一个字段。

### 两列表格

至少三个分类共享“类别 → 内容”“阶段 → 动作”“功能 → 用户价值”等稳定关系，且读者需要同时看到全貌时，使用两列表格：

```md
| 数据类别 | 可采集内容 |
| --- | --- |
| 输入条件 | 菜谱版本；食材重量、温度与形态；环境与设备状态 |
| 过程状态 | 温度曲线；转速与火力；重量与视觉变化 |
| 控制动作 | 火力；翻炒；投料；调味；步骤切换条件 |
| 最终结果 | 出品指标；评分；投诉、剩餐与复购 |
```

表格内部遵守：

- 表头说明真实关系，不使用“项目”“详情”等空泛词。
- 优先保持两列，避免为了视觉丰富增加没有决策价值的列。
- 用顿号连接同类字段，用分号区分子组。
- 单元格保持短语化；需要多段论证时回到正文小节。
- 精确值、单位、状态或版本需要独立比较时，再增加必要列。

### 保留无序列表

以下内容即使较长，也应保留列表：

- 每项是独立风险、约束、判断或验收项。
- 每项需要分别解释、链接或后续扩展。
- 读者需要逐项扫描、选择或核对。
- 项目之间没有稳定的重复字段，表格会制造虚假的二维关系。

不要为了减少页面高度牺牲这些边界。

## 纵向密度检查

交付前从读者视角检查：

1. 一个屏幕内能否看见同一问题的主要分类？
2. 是否存在连续两屏都只有短项目符号、却没有独立解释？
3. 删除项目符号后，内容是否只是一个自然句子？如果是，改为行内并列。
4. 多组列表是否共享相同关系？如果是，考虑两列表格。
5. 表格是否仍能在窄屏滚动或换行后辨认每行对象？如果不能，改用紧凑定义行。

## 不要交给渲染器猜

- 不根据项目数、字符长度或“包括”自动把列表转换成表格。
- 不用全局缩小列表间距解决特定文档的结构问题；操作步骤和风险清单仍需要呼吸感。
- 不让依赖项目复制一份“紧凑列表”CSS。若未来确实需要新的显式语义组件，应在 Docs Engine 中定义稳定接口，再由内容作者明确选择。
