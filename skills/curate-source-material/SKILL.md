# 原始素材忠实整理

## 目标

把一份原始素材重组成读者能快速抓住主干的 Docs Engine 文档，同时保证每个陈述都能回溯到素材本身。整理的价值在于结构、密度和可读性，不在于新增内容。

## 核心边界（忠实性契约）

- 只重组、压缩、合并与去重素材中已有的信息。不引入外部知识、数据、案例或结论；没有依据的补全一律不写。
- 不与项目已有文档的观点混写。需要关联已有文档时只添加链接，不把两边内容揉成新的论述。
- 保留素材的关键术语、数字、人名、时间和限定词。素材没有回答的问题标注“原文未提及”，不要替作者补答案。
- 观点归属原作者：必须保留原始措辞的判断用 `>` 引用；转述时不得改变论断强度（例如把“可能”写成“一定”，把个例写成规律）。
- 素材内部前后矛盾时，并列呈现两处说法并注明各自位置，不做仲裁。

## 工作流

### 1. 先给全局，再给细节

1. 用唯一 H1 概括素材主题。
2. 开头必须有总览：先用一段导语说明素材来源、讨论对象和读完能获得什么；紧接着用“核心结论”小节（宿主支持 frontmatter 时同时填写 `summary`，正文内用一个 `Callout` 承载）总体展示全文要点，让读者不读全文也能带走主干。
3. 正文按主题重组，不默认按素材的叙述顺序流水铺开；只有时间演进本身是重点时才使用 timeline。
4. 素材中反复出现、分散多处的同一话题合并到同一节，并去掉重复表述。

### 2. 压缩连续短行

视频转写和访谈稿会产生大量“一行一个短语”的枚举，逐行照搬会让一整屏只显示十几个词。三个以上连续短行必须重组：

- 同类名词合并为一句行内并列，用顿号相连。
- 三个以上分类共享“类别 → 内容”同一关系时，使用两列表格，让读者一屏看见全貌。
- 二到四个需要一行解释的分类，用加粗引导词的紧凑定义行。

具体判断标准和示例按 author-technical-docs 的 [信息密度与紧凑表达](../author-technical-docs/references/information-density.md) 执行。

### 3. 结构与图表

- 只有素材本身描述了流程、层级、状态或对比时才作图；不要为了“更丰富”把并列要点画成流程图。
- 图表选型按 author-technical-docs 的 [图表选择与编排](../author-technical-docs/references/diagram-selection.md) 执行：层级分类用树形图，流程与分支才用 `flowchart`，节点换行用 `<br/>`。
- 图的节点和边标签只使用素材中的词汇，不引入素材没有的抽象概念。

### 4. 交付前自查

1. 逐节对照素材：每个陈述能指回原文出处；删除所有无来源的句子。
2. 全文检索连续短行列表：不应存在三行以上、每行一个短语的枚举。
3. 确认开头总览独立成立：只读 H1、导语和核心结论就能复述素材主干。
4. 在宿主正文宽度下检查总览、表格与图表的渲染。

## 输出要求

- 交付时说明：素材范围、主要结构决策、忠实性检查结果，以及哪些内容因无来源或与主题无关被舍弃。
- 只创建或修改用户指定的目标文档；不要顺手改动项目里其他文档、运行时组件或宿主配置。
