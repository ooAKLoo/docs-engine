# AI 对话导出整理规范

本文说明如何把一份 ChatGPT、Codex 或其他 AI 产品导出的长对话，整理为结构清晰、可连续阅读、同时能够追溯原文的单篇文档。

这是一份仓库内的专项编辑参考，不是 Docs Engine 的运行时能力、依赖方契约或通用 Agent Skill。除非具体任务明确要求使用，否则不应自动套用到其他文档。

## 目标产物

一轮完整整理通常保留两个层次：

| 产物 | 用途 | 编辑原则 |
|---|---|---|
| 结构化主文档 | 日常阅读、讨论、决策和引用 | 重排结构、压缩重复、清理导出噪声，但保留观点演化与关键原话 |
| 原始归档 | 审计、追溯和防止信息丢失 | 完整保存原始导出，不做内容删改 |

如果产品只允许展示一篇文档，默认展示结构化主文档；原始归档作为独立源文件保留，不进入主导航。

## 主文档保留什么

必须保留会影响理解、产品设计或决策的内容：

- 用户问题中的真实背景、约束、反例和判断依据。
- 回答中的核心观点、论证过程、风险、边界和待验证事项。
- 产品功能点、目标用户、使用场景、商业模式与技术方案。
- 使命、愿景、定位语、Slogan 和投资人表达，即使仍有多个候选版本。
- 同一观点在不同轮次中的修正、收敛和演化。
- 有实际支撑作用的来源链接、数据与案例。

“去重”不等于只留下最后一个结论。如果重复内容体现了逻辑演化，应保留演化节点，并删除没有新增信息的复述。

## 主文档删除什么

以下内容属于对话载体或导出过程产生的噪声，不进入结构化主文档：

| 噪声类型 | 常见形式 | 处理方式 |
|---|---|---|
| 日期和时间戳 | `2026/8/1 21:02:55` | 删除；原始归档保留 |
| 工具调用状态 | `Used personal_context tool` | 删除整个状态块 |
| 搜索过程 | `Searching the web`、`Searched 12 websites` | 删除搜索状态；正式回答实际引用的来源可保留 |
| 执行耗时 | `Worked for 13m 26s` | 删除 |
| 进度摘要 | `Extracting...`、`Sharpening...`、`Refined...` | 删除；不要当作正式回答或思维链展示 |
| 导出占位符 | `document:`、空状态标题 | 删除 |
| 纯迎合套话 | “你的直觉是对的”“完全正确”“对，我明白” | 删除或改写为直接结论 |

这些执行痕迹不是用户需要阅读的正式推理。它们也不应被包装成引用块或 Callout，否则会在视觉上获得不应有的权重。

## 如何处理问题

每轮只显示一个“原始问题”入口，但问题文本可以经过编辑：

1. 合并同一轮中反复补充的问法。
2. 删除口头停顿、重复铺垫和无意义转折。
3. 保留问题的目标、背景、限制条件、对比对象和关键假设。
4. 不把回答中的新结论倒灌进问题。
5. 不把问题压缩成无法解释回答内容的一句话。

推荐结构：

```markdown
### 第 N 轮｜能够概括讨论推进方向的标题

#### 原始问题

经过润色和合并的问题正文。

#### 原始回答

清理导出噪声后的回答正文。
```

“原始问题”表示它对应原始提问轮次，不表示必须逐字复制聊天输入。

## 如何处理回答

先删除执行痕迹，再处理语言和结构，避免误把状态摘要当成观点。

### 删除纯套话

纯确认句没有信息增量，可以直接删除：

```text
你的直觉是对的。
完全正确。
对，我明白。
```

### 保留套话后的判断

同一句中既有迎合表达又有有效判断时，只删除迎合部分：

```text
整理前：对，机制上很像 CUDA，但不能直接把 Rova 说成“个人 AI 时代的 CUDA”。
整理后：机制上很像 CUDA，但不能直接把 Rova 说成“个人 AI 时代的 CUDA”。
```

```text
整理前：你这个担心是成立的，而且我觉得应该反过来定义架构……
整理后：这个风险成立，因此应该反过来定义架构……
```

### 保留观点演化

当后续回答推翻或修正前文时，不要只留下最终答案。应明确呈现：

```text
初始判断 → 用户提出反例 → 修正后的判断 → 对产品或战略的影响
```

如果两段只是不同措辞表达同一结论，则合并；如果新增了条件、边界或因果关系，则保留。

## 单篇文档的信息架构

长对话优先整理为一篇主题主文档，通过目录建立全貌，而不是按聊天轮次拆成大量短文档。

推荐层级：

```text
H1  文档总主题
H2  主题阶段或决策域
H3  对话轮次及其推进方向
H4  原始问题 / 原始回答
H5  回答内部原有的小节
```

对话顺序不是不可改变的时间线。可以按照“问题定义 → 产品方向 → 用户价值 → 商业模式 → 壁垒 → 技术可行性”重排轮次，但应确保观点的前提先于结论出现。

## 控制纵向信息密度

不要把大量短字段机械地拆成一项一行。根据关系选择表达方式：

- 同一类别下的少量短词：使用紧凑定义行。
- 多个类别共享“类别 → 包含内容”：使用两列表格。
- 需要逐项解释、顺序或行动状态：保留列表。
- 使命、愿景和 Slogan：保留独立展示，但避免把每个普通短句都升级成标题。

例如，设备可采集数据适合使用紧凑表格：

| 数据类别 | 可采集内容 |
|---|---|
| 输入条件 | 菜品版本、食材重量、初始温度、含水率、调料浓度、环境参数、设备状态 |
| 过程状态 | 锅体与食材温度、电流与扭矩、转速、火力、重量、视觉状态、投料时间点 |
| 控制动作 | 火力变化、搅拌速度、投料顺序、翻炒动作、阶段切换 |
| 最终结果 | 成品重量、烹饪时长、人工接管、失败类型、口味评分、复购与退菜反馈 |

## Markdown 清理

发布前检查以下问题：

- 每组 `**`、反引号、链接和代码围栏完整闭合，不跨越两个独立标题。
- 正文标题可以保留行内强调，但目录、导航标签和锚点只展示可见纯文本。
- 不把两行共同包在一对 `**` 中；需要两行加粗时，每行分别闭合。
- 标题层级连续，不能为了视觉大小跳级。
- 引用块只保留真正的原话或需要强调来源身份的内容。
- 搜索结果列表如果没有在正文中承担证据作用，应从主文档删除。

## 完成检查

- [ ] 主文档与原始归档的职责明确，原始归档未被覆盖。
- [ ] 每轮问题已经去重和润色，但关键约束没有丢失。
- [ ] 产品功能、使命、愿景、Slogan 和关键投资人表达仍然存在。
- [ ] 重复观点已合并，观点演化仍然可追踪。
- [ ] 日期、工具调用、搜索状态、耗时、进度摘要和导出占位符已从主文档删除。
- [ ] 纯迎合套话已删除，套话后的实质判断已直接表达。
- [ ] 长短列表、表格和标题的选择支持快速建立全貌。
- [ ] Markdown 标记完整，目录不显示 `**`、反引号或链接语法。
- [ ] 在实际文档宿主中检查目录、锚点、表格和长文滚动体验。

## 适用边界

本文只适用于明确要求整理 AI 对话、访谈式问答或聊天导出的任务。普通技术文档、产品文档和依赖 Docs Engine 的项目不会因为本文存在而自动应用这些删除规则。

如果未来需要把这套流程自动化，应另行设计显式调用的导入工具或命令，并要求用户主动选择“结构化整理”模式；不要在通用 Markdown 渲染器中根据文字特征自动删除内容。
